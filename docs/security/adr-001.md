# ADR-001: Enforce security rules in the database, not only in the API

- **Status:** Accepted (Sprint 4, November 2026)
- **Findings:** [SEC-01](findings.md) (#36), SEC-02 (#37), SEC-03 (#38); also covers part of SEC-06

## Context

All three findings we fixed in the Sprint 4 audit came from paths that skip our FastAPI backend:

- The browser signs up directly with Supabase Auth. Our API never sees a sign-up, so it couldn't stop the old `kitchen@puborder.test` rule (SEC-01) or a non-Vanderbilt address (SEC-02).
- The public anon key plus a student's token lets anyone call database functions such as `place_order` directly. A limit enforced only in `POST /orders` (SEC-03) would be skipped by calling the function instead.

A check that lives only in the API protects only the requests that pass through it.

## Decision

Every rule that protects data or other users is enforced in Postgres, in a migration:

- New accounts are always students. Kitchen access comes only from a deliberate `profiles.role` update (`202611120001_kitchen_role_by_grant.sql`).
- A trigger on `auth.users` refuses any account, or email change, outside `@vanderbilt.edu` (`202611120002_vanderbilt_signup.sql`).
- `place_order` enforces the per-student order limits: 3 in progress, 5 per 10 minutes (`202611120003_order_limits.sql`).

The API and frontend can check the same rules earlier to show a friendly message, but the database is what enforces them. The API maps the database's error codes (for example `PT429`) to short user-facing messages.

## Consequences

- The rules hold for every caller: the browser, our API, or a script using the public key.
- Each rule has a SQL regression test in `supabase/tests/` that CI runs against a fresh local database, so it fails before the fix and passes after.
- Every rule change is a migration that someone has to apply to the hosted project in filename order. The README deploy steps list this.
- Database error codes become part of the API's contract, so a migration that changes one needs a matching backend change and test.
- Some settings can't live in Postgres, such as Supabase's **Confirm email**. They stay in the Supabase dashboard, outside version control, and the README deploy steps record them.
