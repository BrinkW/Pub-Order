## Notes on the fixes

All three fixes follow [ADR-001](adr-001.md): security rules are enforced in the database, because sign-up and direct database calls never pass through our API.

- **SEC-01:** migration `202611120001_kitchen_role_by_grant.sql` makes every new account a student. Kitchen access now comes only from a deliberate `profiles` update (README, deploy step 4). Existing kitchen accounts keep their role.
- **SEC-02:** migration `202611120002_vanderbilt_signup.sql` adds a database trigger that refuses any account, or email change, outside `@vanderbilt.edu`. It has to be in the database, because sign-up never passes through our backend. The sign-up form says so before trying. Proving the student owns the address is the hosted project's **Confirm email** setting (README, deploy step 2), which a migration can't set.
- **SEC-03:** migration `202611120003_order_limits.sql` limits each student, inside `place_order`, to 3 orders in progress and 5 orders per 10 minutes, and the API answers 429 with the reason. Because the check is in the database, it also covers direct calls (SEC-06). A per-student lock stops two simultaneous requests from both slipping under a limit.

## Why the Low findings are Low, and what happens next

- **SEC-04:** only kitchen staff can make these changes, so it needs an insider, and it exposes no data. After SEC-01 every kitchen account is granted to one named person, which removes the shared login. PR #39 adds the backend log the A09 checklist asks for: every 401 and 403 is recorded with method, path and client, never a token. Next: an audit table written by the three staff functions.
- **SEC-05:** Appendix C names missing headers as an example of Low. React escapes all output, and Semgrep finds no raw-HTML rendering. Next: set the headers in `serve.py`.
- **SEC-06:** the database re-checks the items, quantities, availability and meal rule, and caps a customization at 200 characters. React shows it as plain text. A direct call only changes the caller's own order. Next: check customizations against the same allow-list inside `place_order`.
- **SEC-07:** the actions come from GitHub and Supabase, and CI holds no secrets that a moved tag could steal. Next: pin each action to a commit SHA.
- **SEC-10:** reachable only through the linter, never through user input, and not in the built app. The only available fix downgrades ESLint. Revisit when ESLint ships a patched `minimatch` (owner: Brink).

The 4 gitleaks results (scans #7–10) are false positives, not findings: a made-up UUID used as a test idempotency key. They are suppressed with that reason in `.gitleaksignore`.
